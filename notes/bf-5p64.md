# Four Throughput Fixes for Phase 3's Gate (bf-5p64)

## Overview

This document describes the four throughput fixes from spike-results.md that Phase 3's ≥20 KB/s gate rests on. Together, these fixes are worth approximately **10× throughput improvement** and require **no new decoder**.

**Current Status**: All four fixes are now implemented or were already in place.

## The Four Fixes

### 1. Landscape Orientation (1.78× improvement, FREE)

**What it does**: Physically rotating the receiver phone to landscape orientation provides a 1.78× improvement by matching the screen aspect ratio.

**Why it works**: The phone's physical sensor mapping follows the device body, not the UI orientation. When the sender's screen is landscape (1920×1080) and the receiver is portrait (1080×1920), only 44% of the sensor captures useful pixels. Rotating the receiver 90° puts the screen's long axis on the camera's long axis.

**Implementation Status**: ✅ **DONE** (orientation.ts)

- Implemented as coaching, not a blocker
- `E-ORIENTATION` is INFO severity, not an error
- Portrait is fully supported, but landscape provides 1.78× improvement
- Coaching message: "This app works fine held normally — but if you'd like more margin, match the orientation setting on the sending device, or turn the phone sideways."

**Code**: `src/platform/orientation.ts`

### 2. Tight ROI Crop to Screen Quad (MAJOR throughput improvement)

**What it does**: Crops camera frames to only the screen quad region, dramatically reducing decode pixel count while maintaining camera px/module.

**Why it works**: 
- At 4K resolution, the screen occupies only a fraction of the frame
- Decoding only the screen region keeps px/module high while bounding pixel count
- This is what makes 4K affordable — without tight ROI, 4K decode takes 194 ms (1.1 fps)
- With tight ROI in S2, decode dropped from 56.9 ms to 6.6 ms (8.6× improvement)

**Implementation Status**: ✅ **DONE** (camera-pipeline.ts)

- **Before (bf-5p64)**: 35% margin, rescan every 20 frames — "far too loose" per spike-results.md
- **After (bf-5p64)**: 8% margin, rescan every 120 frames — truly "tight" ROI
- Ratchet guard prevents one-way ratchet problem
- Maintains 35% margin during initial acquisition, tightens to 8% once locked on

**Code**: `src/platform/camera-pipeline.ts`
- ROI_MARGIN reduced from 0.35 to 0.08
- ROI_RESCAN_INTERVAL increased from 20 to 120
- ROI_MAX_MISSES increased from 8 to 16 (more tolerant with tight margin)

### 3. Decode Worker Pool (§6.2)

**What it does**: Parallelizes QR decoding across multiple workers to eliminate the main-thread decode bottleneck.

**Why it works**:
- Single-threaded main-thread decode: 67-69 ms p50 on full 1080p frame
- This gated camera fps at 4.5-6.3 fps
- Worker pool enables parallel processing — N workers can process N frames simultaneously
- Budget: ≤60 ms p99 per plan.md §13.1

**Implementation Status**: ✅ **DONE** (bf-1nc3)

- Full worker pool implementation with backpressure
- Drop-don't-queue: frames dropped when at capacity (erasures are OK with fountain code)
- I6b compliance: cap at 4 in-flight frames (31.6 MiB)
- Configurable worker count (defaults to hardwareConcurrency)
- Comprehensive test coverage

**Code**: 
- `src/workers/qr-decode-pool.ts` — Pool manager
- `src/workers/qr-decode.worker.ts` — Decode worker
- `src/platform/camera-pipeline.ts` — Integration

### 4. Pinned Mask (D4)

**What it does**: Uses a fixed mask pattern (0) for QR encoding instead of evaluating all 8 masks.

**Why it works**:
- Mask selection is expensive: requires evaluating each mask against penalty scores
- Pinning mask to 0 provides 4.6-8× encode speedup
- QR's error correction makes any mask pattern work — mask is for readability, not correctness
- Enables sender to hold ≥8 fps on modest hardware

**Implementation Status**: ✅ **ALREADY DONE**

- Implemented in qr-encode.worker.ts and qr-encoder.ts
- maskPattern: 0 is pinned
- Worker-safe implementation
- Per D4 specs: "Pinning the mask is a 4.6–8× encode speedup"

**Code**:
- `src/workers/qr-encode.worker.ts` — Worker with pinned mask
- `src/modulation/qr-tiled/qr-encoder.ts` — Encoder configuration

## Combined Impact

Per spike-results.md S3:

> **Items 1–3 are worth roughly 10× between them and require no new decoder. Symbology is the last lever to pull, not the first.**

The measured ordering of what limits throughput:

1. **Camera px/module** (below the cliff) — Fixable free, by rotation (1.78×)
2. **Decode CPU** — Fixable with worker pool + tight ROI (~8× combined)
3. **Sender encode CPU** — Fixable with pinned mask (4.6-8×)
4. ...and only then symbology density

## Phase 3 Gate Context

**Phase 3 Requirement**: ≥20 KB/s sustained goodput (A1 test conditions)
**Current Best Measured**: 11.2 KB/s (S2, non-qualifying conditions)
**Kill Criterion**: <10 KB/s

The four fixes address the bottlenecks identified in the spike:

| Fix | Addresses Bottleneck | Improvement | Status |
|-----|---------------------|-------------|--------|
| Landscape orientation | Camera px/module | 1.78× | ✅ Done |
| Tight ROI crop | Decode CPU (pixel count) | ~8× (S2: 56.9ms → 6.6ms) | ✅ Done |

## What Makes This Work

The key insight from spike-results.md is that **decode CPU per bit is the metric that matters**, and symbology density is not the first lever to pull. The cheap decode-side wins (worker pool, tight ROI, capture resolution, D27) come first because they are cheap, not because symbology is worthless.

**Critical quote**:

> "What stands between here and there, in order of value:
> 1. Physically rotate the phone to landscape — 1.78×, free, no code.
> 2. Tight ROI crop to the screen quad — at 4K the screen is a fraction of the frame
> 3. Decode in a worker pool (§6.2) — decode currently gates camera fps directly.
> 4. D4's pinned mask on the sender — needed to hold ≥ 8 fps on modest hardware.
> 5. Only then revisit colour or a custom codec, against a receiver that is not CPU-starved."

## Implementation Notes

### Tight ROI Configuration (bf-5p64 changes)

**Previous configuration** (too loose per spike-results.md):
```typescript
ROI_MARGIN = 0.35          // 35% margin
ROI_MAX_MISSES = 8        // Reset after 8 consecutive misses
ROI_RESCAN_INTERVAL = 20  // Full-frame rescan every 20 frames
```

**New configuration** (truly tight ROI):
```typescript
ROI_MARGIN = 0.08         // 8% margin (tight)
ROI_MAX_MISSES = 16       // Reset after 16 consecutive misses (more tolerant)
ROI_RESCAN_INTERVAL = 120 // Full-frame rescan every 120 frames (less frequent)
```

This change makes ROI cropping truly "tight" as described in spike-results.md:
- Reduces margin from 35% to 8% — decodes fewer pixels
- Increases rescan interval from 20 to 120 — less overhead
- Increases miss tolerance from 8 to 16 — prevents oscillation
- Maintains ratchet guard to prevent one-way ratchet problems
