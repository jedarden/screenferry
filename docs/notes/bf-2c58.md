# bf-2c58: Reconcile whole-file hash contradictions

## Task
Reconcile three contradictory statements about whether the whole-file hash is mandatory or optional.

## Contradiction found
- §7.2 stated: "Mandatory. concept.md constraint 4 makes byte-exact reconstruction non-negotiable and names this as the verification."
- §3.3 stated: "...plus an **optional** whole-file hash from an incremental WASM hasher."
- §7.4 stated: "The whole-file hash (§7.2) is, and is **optional**."

## Root cause
Two of three sections were not updated when the whole-file hash was made mandatory. The earlier revision had made it optional "on very large files" — i.e., dropped the guarantee exactly where E5 (source mutated during a 10-hour read) is most likely and the stakes are highest.

## Resolution
Updated both §3.3 and §7.4 to correctly reflect that the whole-file hash is **mandatory** per concept.md constraint 4, which makes byte-exact reconstruction non-negotiable.

### Changes made
1. **§3.3** (line 231-234): Changed "optional whole-file hash" to "mandatory whole-file hash" and added explicit reference to concept.md constraint 4.
2. **§7.4** (line 779-780): Changed "The whole-file hash (§7.2) is, and is optional" to "The whole-file hash (§7.2) **is** a content-integrity hash and is mandatory per concept.md constraint 4."

Both sections now agree with §7.2, which already correctly stated the hash is mandatory.

## Verification
All three sections now consistently state that the whole-file hash is mandatory, ensuring the verification mechanism for byte-exact reconstruction (concept.md constraint 4) is properly documented throughout the plan.
